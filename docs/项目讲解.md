## 一、项目定位与比赛要求对应

本项目面向 TikTok Shop / 电商带货短视频场景，目标是让商家输入商品信息、上传素材后，系统自动完成：

- 商品信息理解。
- 带货脚本生成。
- 分镜规划。
- 视频片段生成。
- 视频拼接与后处理。
- 成片预览与下载。
- 生成过程追踪。
- 基于 mock 数据的效果看板和优化建议。

比赛任务中提到的重点可以拆成三层：

| 层级          | 比赛关注点                                                 | 当前实现           |
| ------------- | ---------------------------------------------------------- | ------------------ |
| P0 基础生成   | 商品输入、素材上传、脚本生成、视频生成、任务进度、预览下载 | 已完成             |
| P1 Agent 增强 | 素材理解、RAG 智能分镜、分镜编辑、失败重试、trace、数据看板 | 已完成             |
| P1.6 剧本方法论 | 参考视频库、参考视频拆解报告、参考打法驱动剧本生成，贴合“找参考 -> 提炼方法论 -> 生产剧本”链路 | 已完成 |
| P2 扩展方向   | 更真实的投放数据、A/B 测试、部署运维、合规审核             | 当前保留为后续扩展 |

项目当前主线不是“单纯前端页面 + 一个后端接口”，而是一个多服务协作的 AIGC 工作流系统：

```text
前端负责交互
Node 负责业务 API、数据库、任务状态和文件
Python 负责 Agent、模型调用和视频生成工作流
FFmpeg 负责媒体拼接和后处理
```

## 二、当前完成内容总览

### 2.1 P0 已完成内容

P0 是最基础的端到端生成链路，核心目标是“能从商品信息生成一条视频”。

- 素材库：上传图片/视频，保存到 `storage/uploads`。
- 商品建模：标题、卖点、目标人群、使用场景、画幅。
- 脚本生成：调用文本模型生成结构化 JSON。
- 分镜生成：每个分镜包含描述、镜头运动、字幕、BGM 提示、时长。
- 视频生成：调用 Seedance 生成每个分镜视频。
- 视频拼接：使用 FFmpeg 拼接分镜，并保留音频。
- 任务系统：任务状态、分镜状态、错误信息、SSE 实时推送。
- 预览导出：在线播放最终 MP4，并支持下载。

### 2.2 P1 已完成内容

P1 是在 P0 基础上增强“智能体”和“可控编辑”能力。

- Python FastAPI Agent 服务，端口 `8790`。
- LangGraph 工作流，用于智能剪辑和视频生成流程编排。
- 素材分析 Agent：为素材生成标签、摘要、embedding 向量。
- 素材相似度检索：让剪辑计划可以选择更合适的素材。
- 智能剪辑 Agent：根据商品、脚本、素材生成分镜级剪辑计划。
- 参考视频库：支持上传自有参考视频、录入站外参考链接，并保存为 `ReferenceVideo`。
- 参考视频拆解 Agent：通过 FFmpeg 抽关键帧，调用豆包模型生成 caption 和结构化拆解报告。
- 参考打法驱动剧本生成：新建视频时可选择 `ReferenceVideoAnalysis`，脚本会复用其 Hook、分镜结构、字幕风格和 CTA，并改写为当前商品。
- Retry Agent：根据失败原因做重试决策，例如修正时长、简化 prompt。
- Python 视频 Pipeline：脚本生成、视频生成、回调 Node、拼接、后处理。
- 分镜编辑：支持修改单个分镜 prompt、字幕、素材等。
- 单分镜重生成：重生成一个分镜后重新拼接最终视频。
- 字幕/BGM 后处理：字幕渲染已接入，BGM/TTS 保留扩展点。
- Agent trace：记录关键步骤，前端可查看生成过程。
- 数据看板：展示生成因子、转化效果和中文 Agent 优化建议。
- 冒烟测试脚本：`scripts/smoke-p1.ps1` 支持轻量测试和真实视频测试。

### 2.3 当前版本的核心价值

当前版本最重要的变化是：系统不再只是“生成视频”，而是开始具备 Agent 工作流特征。

具体体现为：

- 生成前：分析素材、拆解参考视频，理解商品和可复用打法。
- 生成中：通过 LangGraph 编排脚本、分镜、视频、重试、拼接。
- 失败时：Retry Agent 根据错误决定如何调整参数。
- 生成后：记录 trace，并在数据看板里给优化建议。
- 用户侧：可以编辑单个分镜，而不是只能重新生成整条视频。

## 三、整体架构设计

### 3.1 当前采用的架构

当前架构是：

```text
React 前端 -> Node Express 主后端 -> Python FastAPI Agent
                         |
                         -> Prisma + SQLite
                         -> storage 本地文件
                         -> SSE 进度推送
```

```mermaid
flowchart LR
  Web[React 前端] --> API[Node Express API]
  API --> DB[(SQLite / Prisma)]
  API --> Storage[storage 本地文件]
  API --> SSE[SSE 任务进度]
  API --> Agent[Python FastAPI Agent]
  Agent --> LangGraph[LangGraph 工作流]
  LangGraph --> TextModel[Doubao 模型服务]
  LangGraph --> VideoModel[Seedance 视频模型]
  LangGraph --> FFMPEG[FFmpeg 拼接/后处理]
  Agent --> Callback[Node internal callback]
  Callback --> API
```

### 3.2 为什么不是全 Node，也不是全 Python

P0 已经用 Node + Express + Prisma 跑通了前端 API、数据库、上传、任务状态和 SSE。如果全部改成 Python，会破坏已有稳定链路，迁移成本高。

但 Agent、LangGraph、模型编排、视频工作流更适合 Python，所以 P1 采用折中架构：

- Node 继续做业务网关。
- Python 专门做 AI 能力。
- 前端只调用 Node，不直接调用两个后端。
- Node 和 Python 通过 HTTP 内部接口协作。

这种结构和很多真实项目类似：业务后端负责稳定业务，AI 服务负责模型和智能体。

### 3.3 服务职责边界

| 服务         | 主要职责                                                      | 不适合承担                           |
| ------------ | ------------------------------------------------------------- | ------------------------------------ |
| React 前端   | 页面交互、表单、任务展示、视频预览、trace 展示                | 直接保存数据库、直接调用模型         |
| Node API     | 前端 API、Prisma、文件上传、静态资源、SSE、任务记录、回调入口 | 复杂 Agent 编排、长流程 AI 工作流    |
| Python Agent | 素材分析、智能剪辑、Retry、LangGraph、模型调用、视频 pipeline | 面向前端的全部业务 API、Prisma owner |
| Python 内部 FFmpeg 能力 | 视频拼接、音频保留、字幕后处理                         | 决策逻辑、任务状态管理               |

### 3.4 P1.5 Agent 深度增强后的最终链路

P1.5/P1.6 之后，系统边界进一步收敛：Node 不再承担 AI 模型 runtime，只保留 API 网关、Prisma/SQLite 数据库 owner、素材/参考视频上传、静态资源、任务状态、SSE 和 Python 回调入口；Python 是唯一 AI runtime，负责视觉 caption、参考视频拆解、外部 embedding、RAG 检索、LangGraph Agent 规划、Seedance 分镜生成、Retry、拼接和后处理。

```mermaid
flowchart LR
  Material[素材] --> Caption[视觉 Caption]
  Caption --> Embed[Embedding API]
  Embed --> RAG[RAG TopK]
  Reference[参考视频拆解] --> Script[参考驱动脚本]
  Script --> RAG
  RAG --> LLM[LLM Editing Agent]
  LLM --> Plan[Saved EditingPlan]
  Plan --> Shot[Shot Records]
  Shot --> Video[Seedance per-shot generation]
  Video --> Post[Python FFmpeg stitching/postprocess]
```

这里的“智能分镜/剪辑计划”是生成前规划，不是专业 NLE 时间线剪辑，也不是让 LLM 直接修改已经生成好的 MP4 文件。Agent 真正决定的是每个分镜的生成策略：使用哪个素材作为参考、prompt 如何组织、字幕和卖点如何落位、分镜时长如何约束、失败后如何重试。视频片段仍由 Seedance 逐分镜生成，最终由 Python 内部的 FFmpeg 工具完成拼接和后处理。

外部 embedding 的作用也需要明确：embedding 向量不会直接喂给豆包文本模型。向量只用于检索和排序素材，真正进入 LLM 上下文的是素材的 caption、summary、tags、相似度 score 和少量文件元信息。这样既能体现 RAG 检索能力，也避免把高维向量原样塞进文本 prompt，造成 token 浪费和语义不可读。

### 3.5 P1.5 的核心架构和算法改动

这一版最重要的变化不是页面多了几个按钮，而是后端职责和 Agent 算法都发生了变化。答辩时可以把它概括为：Node 收敛为稳定业务层，Python 成为唯一 AI runtime，参考视频拆解、素材理解和分镜方案由 `参考打法 + 视觉 caption + embedding + RAG + LLM + LangGraph` 串起来。

| 改动点 | 当前实现 | 技术意义 |
| ------ | -------- | -------- |
| Node 职责收敛 | Node 保留为 API Gateway、Prisma/SQLite owner、文件上传、静态资源、任务状态、SSE 和 Python 回调入口。旧 Node AI runtime 已删除。 | 避免 Node 和 Python 同时做模型编排，架构边界更清晰。 |
| Python 唯一 AI runtime | Python 负责素材分析、视觉 caption、embedding、RAG 检索、LLM Editing Agent、Seedance 视频生成、Retry、单分镜重生成、重新拼接和后处理。 | 让 Agent、LangGraph、大模型调用集中在 Python，符合 Agent 工程习惯。 |
| 素材分析升级 | `Material` 增加 `caption` 和 `embeddingModel` 字段，同时保存 `summary/tags/embeddingText/embeddingVectorJson`。 | 素材库不再只是文件列表，而是可被检索和推理的素材知识库。 |
| 参考视频方法论 | 新增 `ReferenceVideo` 和 `ReferenceVideoAnalysis`，支持参考视频上传/录入、关键帧理解、结构化拆解报告和参考打法复用。 | 对应比赛剧本模块的“找参考 -> 提炼方法论 -> 生产剧本”。 |
| 参考驱动脚本 | `Script` 记录 `referenceAnalysisId`，剧本生成可接收参考拆解报告，复用 Hook、分镜结构、字幕风格和 CTA。 | 让剧本不只是凭空生成，而是有可追溯的参考方法论来源。 |
| embedding provider 化 | P1 早期是 16 维 hash mock；P1.5 改为 provider 结构：mock 模式使用 64 维 fallback，live 模式调用外部 embedding API，当前按你的要求优先使用通义千问 embedding。 | 让 RAG 从“演示用 mock 相似度”升级为真实语义向量检索。 |
| Editing Agent 升级 | 从本地规则函数升级为 `LangGraph + RAG + LLM planning`。 | Agent 不只是封装函数，而是有检索、上下文构造、LLM 规划、校验、fallback 的工作流。 |
| EditingPlan 持久化 | 新增 `EditingPlan` 表保存智能分镜方案、策略、payload 和 trace。 | 生成方案可回看、复用、审计，也能解释“视频为什么这样生成”。 |
| 任务生成强约束 | 创建视频任务时必须带 `editingPlanId`，Shot 从方案写入 `prompt/subtitle/bgmHint/sourceMaterialId/durationSec`。 | 保证视频生成真正使用智能分镜方案，而不是生成完方案后又绕回旧脚本。 |
| Python 视频闭环 | 单分镜重生成和重新拼接已迁到 Python。Node 只触发请求、持久化状态和推送 SSE。 | AI 视频生成和媒体处理闭环集中在 Python，减少割裂。 |

## 四、核心调用链路图

这一章是讲解系统时最重要的部分。建议答辩时重点讲这些图。

### 4.1 端到端主链路

用户从上传素材到得到视频，真实完整链路如下。这里要注意：参考视频拆解服务于“脚本方法论”，素材 RAG 服务于“分镜素材选择”。RAG 不是在视频生成时临时凭空发生的，而是先通过素材分析把素材变成可检索语义资产；生成智能分镜方案时再用这些向量做 TopK 检索，最后把 EditingPlan 真正写入 Shot 并用于视频生成。

```mermaid
sequenceDiagram
  participant U as 用户
  participant Web as React 前端
  participant API as Node API
  participant DB as SQLite/Prisma
  participant Agent as Python Agent
  participant Doubao as Doubao 模型服务
  participant Embed as Embedding 服务
  participant Video as Seedance 视频服务

  U->>Web: 上传素材、填写商品信息
  Web->>API: POST /api/materials
  API->>DB: 保存素材记录
  API-->>Web: 返回素材 URL

  Web->>API: POST /api/materials/:id/analyze
  API->>Agent: POST /materials/analyze
  Agent->>Doubao: 图片素材生成 caption
  Doubao-->>Agent: caption
  Agent->>Embed: summary + tags + caption 生成素材 embedding
  Embed-->>Agent: embedding vector / model
  Agent-->>API: caption / tags / summary / embedding
  API->>DB: 更新 Material.caption/embeddingVectorJson/embeddingModel
  API-->>Web: 展示素材 caption、标签和摘要

  U->>Web: 上传或录入参考视频
  Web->>API: POST /api/references 或 /api/references/upload
  API->>DB: 保存 ReferenceVideo
  Web->>API: POST /api/references/:id/analyze
  API->>Agent: POST /references/analyze
  Agent->>Agent: FFmpeg 抽关键帧
  Agent->>Doubao: 关键帧 caption + 结构化电商拆解
  Doubao-->>Agent: Hook / 痛点 / 分镜结构 / CTA / 可复用模板
  Agent-->>API: ReferenceVideoAnalysisResponse
  API->>DB: 保存 ReferenceVideoAnalysis
  API-->>Web: 展示参考视频拆解报告

  Web->>API: POST /api/scripts + referenceAnalysisId
  API->>DB: 读取 Product + 可选 ReferenceVideoAnalysis
  API->>Agent: POST /scripts/generate + reference_analysis
  Agent->>Doubao: 商品信息 + 参考打法生成结构化脚本
  Doubao-->>Agent: narrative / visualStyle / shots
  Agent-->>API: script payload
  API->>DB: 保存 Script.referenceAnalysisId
  API-->>Web: 返回脚本预览

  Web->>API: POST /api/scripts/:id/editing-plan
  API->>DB: 读取 Script + Product + 已分析 Materials
  API->>Agent: POST /editing/plan
  Agent->>Embed: 构造全局查询并生成 query embedding
  Embed-->>Agent: query embedding
  Agent->>Agent: 与素材 embeddingVectorJson 做余弦相似度 TopK
  Agent->>Doubao: 传入商品/脚本/RAG候选素材，生成智能分镜方案
  Doubao-->>Agent: planned shots + strategy + reasons
  Agent->>Agent: 校验素材ID/去重/修正时长/fallback
  Agent-->>API: EditingPlanResponse
  API->>DB: 保存 EditingPlan
  API-->>Web: 展示智能分镜方案

  Web->>API: POST /api/tasks + editingPlanId
  API->>DB: 校验 EditingPlan 属于当前 Script
  API->>DB: 创建 Task，并从 EditingPlan 写入 Shot
  API-->>Web: 返回 taskId，建立 SSE
  API->>Agent: POST /pipeline/run
  Agent->>Video: 按 Shot prompt + sourceMaterialPath 逐分镜生成视频
  Video-->>Agent: shot_N.mp4
  Agent->>API: callback shot video_ok / trace
  API->>DB: 更新 Shot 状态和 TaskTrace
  API-->>Web: SSE 推送分镜进度
  Agent->>Agent: Python 内部 FFmpeg 拼接和后处理
  Agent->>Agent: 生成 output_p1.mp4
  Agent->>API: callback succeeded + outputPath + trace
  API->>DB: 保存任务结果
  API-->>Web: SSE 推送 succeeded
  Web-->>U: 预览和下载最终视频
```

这条链路体现了系统的完整闭环：

- 前端触发业务和展示结果。
- Node 负责 API Gateway、Prisma 持久化、文件路径、任务状态和 SSE。
- Python Agent 负责参考视频拆解、素材理解、RAG、LLM 分镜规划、Seedance 调用、Retry、FFmpeg 拼接和后处理。
- Doubao/Embedding/Seedance 等外部模型服务负责内容理解、语义向量和视频生成。
- Python 通过 callback 把进度、trace、outputPath 写回 Node，Node 再通过 SSE 推送给前端。

### 4.2 素材分析链路

素材分析是 P1 的基础。如果没有素材分析，后面的智能剪辑只能根据文字脚本生成 prompt，无法利用用户上传的真实商品素材。

```mermaid
flowchart TD
  A[用户上传素材] --> B[Node 保存文件到 storage/uploads]
  B --> C[Node 创建 Material 记录]
  C --> D[前端点击分析素材]
  D --> E[Node POST /api/materials/:id/analyze]
  E --> F[Python Material Agent]
  F --> G[Doubao 模型服务生成 caption]
  G --> H[生成 summary/tags/embeddingText]
  H --> I[Embedding Provider 生成向量]
  I --> J[Python 返回 caption/tags/summary/vector/model]
  J --> K[Node 更新 Material 分析字段]
  K --> L[前端展示 caption/标签/摘要]
  K --> M[后续 RAG 检索复用 embeddingVectorJson]
```

相关文件：

| 文件                                                | 作用                       |
| --------------------------------------------------- | -------------------------- |
| `apps/web/src/pages/MaterialLibrary.tsx`            | 素材库页面，触发上传和分析 |
| `apps/api/src/modules/material/material.router.ts`  | Node 素材接口              |
| `apps/api/src/modules/material/material.service.ts` | 保存素材、更新分析结果     |
| `apps/agent/src/agent_app/agents/material_agent.py` | Python 素材分析逻辑        |

P1.5 之后，素材分析不再只是生成几个标签，而是为后续 RAG 建立可检索的素材语义表示：

```mermaid
flowchart TD
  A[上传图片素材] --> B[Node 保存文件和 Material 记录]
  B --> C[Python Material Agent]
  C --> D[Doubao 模型服务 Caption]
  D --> E[caption: 描述商品主体/场景/构图]
  E --> F[summary + tags + caption 拼接为 embeddingText]
  F --> G{MODEL_MODE}
  G -->|mock| H[64 维 fallback embedding]
  G -->|live| I[通义千问 Embedding API]
  H --> J[embeddingVectorJson]
  I --> J
  J --> K[Node/Prisma 保存到 Material]
  K --> L[后续智能分镜复用，不需要每次重新分析素材]
```

各字段的作用：

| 字段 | 来源 | 用途 |
| ---- | ---- | ---- |
| `caption` | 豆包视觉模型，mock 时使用 fallback caption | 把图片内容变成文本语义，例如商品主体、颜色、场景、构图。 |
| `summary` | Material Agent 汇总 | 给前端展示，也参与 embedding 文本。 |
| `tagsJson` | Material Agent 生成 | 快速标记素材类型、场景和商品卖点。 |
| `embeddingText` | `summary + tags + caption` | 送入 embedding provider 的文本，不是直接给视频模型。 |
| `embeddingVectorJson` | embedding provider 返回 | SQLite 中以 JSON 保存的向量，用于 Python 内部余弦相似度计算。 |
| `embeddingModel` | embedding provider 返回 | 记录这条向量来自哪个模型，方便排查和展示。 |

这里要注意两点：

- 早期 P1 是 16 维 hash mock，适合快速证明“能检索”；P1.5 已经改成 provider 结构，mock 模式是 64 维 fallback，live 模式调用外部 embedding API。
- 素材分析通常只需要对素材执行一次。后续生成不同脚本、不同智能分镜方案时，会复用数据库里已经保存的 `embeddingVectorJson`。

### 4.3 参考视频库与拆解报告链路

参考视频链路对应比赛文档里“找参考 -> 提炼方法论 -> 生产剧本”的前两步。它不直接替代素材库，也不会直接进入 RAG 选图；它的价值是把一个优秀带货视频拆成可复用的脚本方法论，再让后续脚本生成借鉴这种打法。

```mermaid
flowchart TD
  A[用户上传参考视频或录入站外链接] --> B[Node 保存 ReferenceVideo]
  B --> C[前端点击生成拆解报告]
  C --> D[Node POST /api/references/:id/analyze]
  D --> E[Python Reference Analysis Agent]
  E --> F[FFmpeg 抽取关键帧]
  F --> G[Doubao 模型服务生成关键帧 caption]
  G --> H[Doubao 模型服务结构化拆解]
  H --> I[Hook/痛点/卖点/分镜结构/风格/CTA/可复用模板]
  I --> J[Node 保存 ReferenceVideoAnalysis]
  J --> K[前端展示拆解报告]
  K --> L[新建视频时作为 referenceAnalysisId 参与脚本生成]
```

拆解报告主要保存这些信息：

| 字段 | 用途 |
| ---- | ---- |
| `hook` | 开头吸引用户的方法，例如痛点提问、强反差、场景代入。 |
| `painPoints` | 参考视频命中的用户痛点，后续脚本可借鉴但要改写到当前商品。 |
| `sellingPoints` | 参考视频如何表达卖点，用于生成当前商品卖点表达。 |
| `shotStructure` | 参考视频的分镜节奏和信息顺序。 |
| `visualStyle` | 画面风格、镜头节奏、场景调性。 |
| `subtitleStyle` | 字幕呈现方式和语气。 |
| `bgmRhythm` | BGM 节奏和情绪变化。 |
| `cta` | 结尾转化动作，例如购物车、限时优惠、下单引导。 |
| `reusableTemplate` | 总结出的可复用打法模板。 |

### 4.4 脚本生成与智能剪辑链路

P0 只有脚本生成，P1 加入剪辑计划，P1.6 又让脚本生成可以引用参考视频拆解报告。剪辑计划的作用是把“脚本文字”变成“可执行的视频生成方案”。

```mermaid
sequenceDiagram
  participant Web as 前端 NewVideo
  participant API as Node Script Router
  participant Agent as Python Agent
  participant Graph as LangGraph Editing Graph
  participant Embed as Embedding Provider
  participant Doubao as Doubao 模型服务
  participant DB as SQLite

  Web->>API: POST /api/scripts + 可选 referenceAnalysisId
  API->>DB: 读取 Product + 可选 ReferenceVideoAnalysis
  API->>Agent: POST /scripts/generate + reference_analysis
  Agent-->>API: narrative / visualStyle / shots
  API->>DB: 保存 Script.referenceAnalysisId
  API-->>Web: 返回脚本

  Web->>API: POST /api/scripts/:id/editing-plan
  API->>DB: 读取 Script + Product + Materials
  API->>Agent: POST /editing/plan
  Agent->>Graph: build_rag_context
  Graph->>Embed: 生成 query embedding
  Embed-->>Graph: query vector
  Graph->>Graph: 素材向量余弦相似度 TopK
  Graph->>Graph: build_llm_payload
  Graph->>Doubao: 商品 + 脚本 + RAG候选素材
  Doubao-->>Graph: planned shots JSON
  Graph->>Graph: validate_plan
  Graph-->>Agent: planned shots / strategy / trace
  Agent-->>API: EditingPlanResponse
  API->>DB: 保存 EditingPlan
  API-->>Web: 返回智能分镜方案
```

剪辑计划会影响：

- 每个分镜的生成 prompt。
- 每个分镜是否使用商品素材。
- 字幕和 BGM 提示。
- 时长是否合法。
- 后续生成失败时的重试空间。

P1.5 的智能分镜方案不是简单规则拼接，而是一个 LangGraph 工作流：

```mermaid
flowchart TD
  A[Script + Product + Materials] --> B[build_rag_context]
  B --> C[构造整支视频全局查询文本]
  C --> D[query embedding]
  D --> E[与素材 embeddingVectorJson 做余弦相似度]
  E --> F[每个分镜取 RAG TopK 候选素材]
  F --> G[build_llm_payload]
  G --> H[LLM Editing Agent]
  H --> I[validate_plan]
  I --> J{素材 ID 是否合法/重复}
  J -->|可修复| K[选择未使用候选素材或置空]
  J -->|通过| L[EditingPlanResponse]
  K --> L
  L --> M[Node 保存 EditingPlan]
```

这个流程里，LLM 看到的是“可读的候选素材上下文”，不是原始向量。传给 LLM 的核心信息包括：

- 商品标题、卖点、目标人群、使用场景。
- 原始脚本的叙事策略、视觉风格和分镜。
- 每个分镜的 RAG 候选素材：`material_id`、`caption`、`summary`、`tags`、`score`、`reason`。
- 约束：只能选择候选素材 ID，素材不相关时可以返回 `null`；时长必须符合视频模型约束；输出结构必须能落库。

因此这里的 RAG 不是“把向量喂给大模型”，而是：

1. 用 embedding 向量做相似度检索。
2. 用 TopK 结果缩小 LLM 可选择的素材范围。
3. 让 LLM 在候选素材、脚本目标和生成约束之间做规划。
4. 再由校验节点修复非法素材 ID、重复素材和不合法时长。

如果素材库只有 3 张相关图片，但脚本有 5 个分镜，系统不会强行每个分镜都塞图片。`validate_plan` 会优先避免重复使用素材；素材不足或不相关时，`sourceMaterialId` 可以为空，该分镜走纯文本视频生成。

相关代码：

| 文件 | 作用 |
| ---- | ---- |
| `apps/agent/src/agent_app/agents/editing_graph.py` | LangGraph RAG + LLM planning + 校验/fallback 主逻辑 |
| `apps/agent/src/agent_app/providers/embedding.py` | embedding provider，mock fallback 或 live 外部 API |
| `apps/agent/src/agent_app/providers/ark_text.py` | 文本 LLM JSON 调用和 mock LLM 输出 |
| `apps/api/src/modules/script/script.router.ts` | 收集候选素材，调用 `/editing/plan`，保存 EditingPlan |
| `apps/api/src/modules/script/script.service.ts` | EditingPlan 持久化和 DTO 转换 |

### 4.5 Python Pipeline 视频生成链路

当前版本中，视频生成由 Python Pipeline 执行。Node 不再走旧的 Node AI runtime，而是创建任务记录后调用 Python `/pipeline/run`。

```mermaid
flowchart TD
  A[前端 POST /api/tasks + editingPlanId] --> B[Node 校验 EditingPlan]
  B --> C[Node 创建 Task]
  C --> D[从 EditingPlan 写入 Shot 记录]
  D --> E[prompt/subtitle/bgmHint/sourceMaterialId/durationSec]
  E --> F[Node 调用 Python /pipeline/run]
  F --> G[Python 加载任务上下文]
  G --> H[LangGraph 生成分镜视频]
  H --> I{分镜是否失败}
  I -->|是| J[Retry Agent 决策]
  J --> K[修正 prompt/时长/参数后重试]
  K --> H
  I -->|否| L[Python callback Node: shot video_ok + trace]
  L --> M[Node 更新 Shot 状态并通过 SSE 推送]
  M --> N{所有分镜完成}
  N -->|否| H
  N -->|是| O[Python 内部 FFmpeg 拼接分镜]
  O --> P[字幕/BGM 后处理]
  P --> Q[Python callback Node: succeeded + outputPath]
  Q --> R[Node 更新 Task 并通过 SSE 推送]
  R --> S[前端预览 output_p1.mp4]
```

关键点：

- 创建视频任务必须带 `editingPlanId`，否则会被 Node 拒绝。
- Node 创建任务和分镜记录，保证数据库统一。
- Shot 不再直接照搬原始脚本，而是从 EditingPlan 写入 `prompt/subtitle/bgmHint/sourceMaterialId/durationSec`。
- Python 执行长耗时 AI 工作流。
- Python 每个关键阶段回调 Node，Node 持久化状态和 trace。
- 前端通过 Node SSE 获取实时进度。

### 4.6 任务状态与 SSE 链路

### 4.7 分镜编辑与单分镜重生成链路

P1 的一个关键增强是“不是整条视频重做”，而是可以单独编辑并重生成某个分镜。

```mermaid
flowchart TD
  A[用户在任务详情页编辑分镜] --> B[PATCH /api/tasks/:taskId/shots/:shotId]
  B --> C[Node 更新 Shot prompt/subtitle/material]
  C --> D[用户点击重生成]
  D --> E[POST /api/tasks/:taskId/shots/:shotId/regenerate]
  E --> F[Node 调用 Python /pipeline/regenerate-shot]
  F --> G[Python 重新生成单个 shot_N.mp4]
  G --> H[Python callback Node: shot video_ok + trace]
  H --> I[Python restitch 重新拼接]
  I --> J[Python callback Node: succeeded + outputPath]
  J --> K[Node 更新 Shot/Task 并通过 SSE 推送]
  K --> L[前端预览新版视频]
```

这比“重新生成全部分镜”更适合真实剪辑工作，因为用户通常只想改一个镜头。当前单分镜重生成和重新拼接已经迁到 Python，Node 只负责触发接口、保存状态和通过 SSE 通知前端。

### 4.8 Retry Agent 链路

Retry Agent 的作用是让失败不是简单终止，而是根据错误类型选择修正方案。

```mermaid
flowchart TD
  A[视频生成失败] --> B[捕获错误信息]
  B --> C[Retry Agent 分析错误]
  C --> D{错误类型}
  D -->|duration 参数错误| E[修正 duration_sec]
  D -->|prompt 过长或不稳定| F[简化 prompt]
  D -->|模型暂时失败| G[保持参数重试]
  D -->|超过次数| H[停止并标记 failed]
  E --> I[记录 trace]
  F --> I
  G --> I
  I --> J[重新调用 Seedance 生成]
  J --> L[Python callback Node: retry trace/shot status]
  H --> K[Python callback Node: failed + errorMsg]
  K --> M[Node 保存错误并通过 SSE 推送]
```

当前已记录的已知问题之一就是 Seedance 1.5 Pro 图生视频偶发 `duration` 参数 400。Retry Agent 会识别 duration 错误，在重试时修正为更稳妥的时长。

### 4.9 Trace 链路

Trace 用来回答“这个视频是怎么生成出来的”。比赛答辩时，这是体现工程完整度和可观测性的部分。

```mermaid
flowchart LR
  A[Python Agent/Node Pipeline] --> B[记录 stage/message/meta]
  B --> C[Node internal trace callback]
  C --> D[Prisma 保存 Trace]
  D --> E[GET /api/traces]
  E --> F[前端任务详情 Trace 面板]
```

Trace 可以记录：

- 脚本生成开始/结束。
- 剪辑计划生成开始/结束。
- 分镜生成开始/成功/失败。
- Retry 决策。
- FFmpeg 拼接。
- 后处理。
- 最终输出。

### 4.10 数据看板链路

数据看板当前是 mock analytics，用于展示 P1 的“生成效果分析”和“Agent 优化建议”。

```mermaid
flowchart TD
  A[前端 Analytics 页面] --> B[GET /api/analytics/summary]
  B --> C[Node 转发或聚合数据]
  C --> D[Python Analytics Agent]
  D --> E[生成中文优化建议]
  C --> F[返回 CTR/CVR/Completion mock 指标]
  E --> G[前端展示建议]
  F --> H[前端展示柱状图]
```

这部分不是为了声称有真实投放数据，而是为了展示系统可以接入效果反馈，未来支持 A/B 测试和投放优化闭环。


调用关系：

- 素材分析：Node `/api/materials/:id/analyze` -> Python `/materials/analyze`
- 素材检索：Node `/api/materials/search` -> Python `/materials/search`
- 参考视频拆解：Node `/api/references/:id/analyze` -> Python `/references/analyze`
- 脚本生成：Node `/api/scripts` -> Python `/scripts/generate`
- 剪辑计划：Node `/api/scripts/:id/editing-plan` -> Python `/editing/plan`
- 视频 Pipeline：Node `/api/tasks` -> Python `/pipeline/run`
- 单分镜重生成：Node `/api/tasks/:taskId/shots/:shotId/regenerate` -> Python `/pipeline/regenerate-shot`

需要强调的是，Node 现在不是 AI runtime。它不再负责文本模型 prompt 编排、RAG 检索、Seedance 调用或视频拼接决策；这些都交给 Python。Node 的价值是业务稳定性：鉴权/路由、Prisma、文件路径、任务状态、SSE 和内部回调。

### 9.2 为什么数据库仍然在 Node

- `Material.caption`：视觉模型对图片素材的中文语义描述。
- `Material.embeddingModel`：记录当前素材向量来自哪个 embedding provider。
- `Material.embeddingVectorJson`：SQLite 中用 JSON 保存向量，Python 读取后用 numpy/余弦相似度检索。
- `ReferenceVideo`：保存参考视频来源，可以是本地上传文件，也可以是站外链接记录。
- `ReferenceVideoAnalysis`：保存参考视频拆解报告，包括 Hook、痛点、卖点、分镜结构、风格、CTA 和可复用模板。
- `Script.referenceAnalysisId`：记录当前脚本使用了哪个参考视频拆解报告，方便前端回看和链路追溯。
- `EditingPlan`：保存智能分镜方案，包含整体策略、分镜 payload 和 Agent trace。
- `Shot.sourceMaterialId`：把智能分镜方案选择的素材真正带入视频生成。

当前没有引入 MySQL、Milvus 或 pgvector，原因是比赛 demo 更重视可运行闭环。SQLite JSON 向量 + Python 余弦相似度足够支撑本地 RAG 原型；后续如果要上生产，可以把 `embeddingVectorJson` 迁移到 PostgreSQL + pgvector 或专门向量库。

当前建议数据库仍由 Node 管理，原因是：

- Prisma 和已有 schema 都在 Node。
- 前端所有业务 API 已经通过 Node。
- Python 如果直接写 SQLite，会带来双写、连接和 schema 同步问题。
- Python 通过 Node internal callback 更新状态，更符合服务边界。

## 十、关键业务流程逐步讲解

### 10.1 创建商品

1. 用户在 `/new` 页面填写商品标题、卖点、目标人群、场景、画幅。
2. 前端调用 `POST /api/products`。
3. Node 使用 Zod 校验请求。
4. Node 通过 Prisma 保存 Product。
5. 前端拿到 productId，用于后续脚本生成。

### 10.2 上传并分析素材

1. 用户在 `/materials` 上传素材。
2. Node 使用 multer 接收 multipart 文件。
3. 文件保存到 `storage/uploads`。
4. Material 表保存文件名、路径、mime、productId。
5. 用户点击“分析素材”。
6. Node 调用 Python `/materials/analyze`。
7. Python 如果拿到图片本地路径，会先调用视觉 caption provider，live 模式使用豆包视觉模型，mock 模式使用 fallback caption。
8. Python 将 `caption + summary + tags` 组织为 `embeddingText`。
9. embedding provider 生成向量：mock 模式为 64 维 fallback，live 模式调用外部 embedding API。
10. Node 保存 `caption/summary/tagsJson/embeddingText/embeddingVectorJson/embeddingModel`。
11. 前端显示标签、摘要、caption 和检索信息。

这一阶段生成的 embedding 会持久化在 SQLite 中，后续生成智能分镜方案时直接复用，不需要每次生成视频都重新分析素材。

### 10.3 拆解参考视频

1. 用户在 `/references` 页面上传自有参考视频，或录入站外爆款视频链接。
2. Node 保存 `ReferenceVideo` 记录和本地文件路径。
3. 用户点击“生成拆解报告”。
4. Node 调用 Python `/references/analyze`。
5. Python 使用 FFmpeg 从视频抽取关键帧。
6. Python 调用豆包模型服务，为关键帧生成 caption，并生成结构化电商拆解。
7. 拆解结果包含 Hook、痛点、卖点、分镜结构、视觉风格、字幕风格、BGM 节奏、CTA、可复用模板和 trace。
8. Node 保存 `ReferenceVideoAnalysis`。
9. 前端展示拆解报告，后续 `/new` 页面可以选择它作为“参考视频打法”。

### 10.4 生成脚本

1. 用户在 `/new` 页面填写商品信息。
2. 用户可以选择一个已拆解的 `ReferenceVideoAnalysis`，也可以不选。
3. 用户点击生成脚本。
4. Node 读取商品信息和可选参考拆解报告。
5. 如果启用 Python 模式，Node 调用 Python `/scripts/generate`，并传入 `reference_analysis`。
6. Python 调用豆包模型服务，要求模型借鉴参考视频的 Hook、分镜结构、字幕风格和 CTA，但必须改写为当前商品。
7. 模型返回结构化 JSON。
8. Python/Pydantic 校验结构。
9. Node 保存 Script，并写入 `referenceAnalysisId`。
10. 前端显示脚本、分镜，并展示“本脚本已使用参考视频打法”。

### 10.5 生成剪辑计划

1. 前端调用 `POST /api/scripts/:id/editing-plan`。
2. Node 读取 Script、Product、Material。
3. Node 只收集已分析素材及其 `caption/summary/tags/embeddingVectorJson`，不强制把素材绑定到某个商品。
4. Node 把上下文传给 Python `/editing/plan`。
5. Python Editing Graph 构造整支视频的全局查询文本，并生成 query embedding。
6. Python 用 query embedding 和素材 embedding 做余弦相似度 TopK，形成 RAG 候选素材。
7. Python 把商品、脚本、RAG 候选素材传给 LLM Editing Agent。
8. LLM 返回每个分镜的建议：
   - prompt
   - subtitle
   - bgmHint
   - duration
   - sourceMaterialId
   - reason
9. Python 校验 LLM 输出：素材 ID 必须来自候选素材，重复素材会尽量换成未使用候选，不相关时允许为空。
10. Node 将结果保存为 `EditingPlan`。
11. 前端展示智能分镜方案。

### 10.6 生成视频

1. 用户点击开始生成。
2. 前端调用 `POST /api/tasks`，必须带上 `editingPlanId`。
3. Node 校验这个 EditingPlan 是否属于当前 Script。
4. Node 创建 VideoTask。
5. Node 从 EditingPlan payload 创建 Shot，并写入 `prompt/subtitle/bgmHint/sourceMaterialId/durationSec`。
6. Node 返回 taskId，前端跳转任务详情页。
7. Node 后台调用 Python `/pipeline/run`。
8. Python Pipeline 依次生成每个分镜视频。
9. 如果 Shot 有 `sourceMaterialId`，Node 会把素材路径传给 Python，Seedance 走图生视频；如果为空，则走纯文本生成。
10. 每个分镜成功后回调 Node 更新 shot。
11. 所有分镜完成后 Python FFmpeg 拼接。
12. 后处理字幕/BGM。
13. Python 回调 Node 更新 task 为 `succeeded`。
14. 前端通过 SSE 收到最终状态。
15. 用户进入预览页播放和下载视频。

### 10.7 单分镜重生成

1. 用户在任务详情页修改某个分镜 prompt 或字幕。
2. 前端调用 `PATCH /api/tasks/:taskId/shots/:shotId`。
3. Node 更新该 Shot。
4. 用户点击重生成。
5. Node 调用 Python `/pipeline/regenerate-shot`。
6. Python 根据最新 Shot prompt、subtitle、sourceMaterialId 和素材路径重新生成单个视频。
7. 新视频替换旧的 `shot_N.mp4`。
8. Python 重新拼接最终视频并后处理。
9. Node 保存新的 outputUrl 和 trace。
10. 前端预览新的成片。

## 十一、Agent、LangGraph 与 Retry 机制

### 11.1 Agent 在项目里的含义

这里的 Agent 不是单纯“调用一次大模型”，而是有任务目标、有输入输出、有工具调用、有失败处理的工作单元。

当前包括：

| Agent           | 输入                 | 输出                     | 作用                 |
| --------------- | -------------------- | ------------------------ | -------------------- |
| Material Agent  | 素材文件信息         | caption、tags、summary、embedding | 把素材转成可检索语义资产 |
| Reference Analysis Agent | 参考视频文件/链接 | Hook、痛点、分镜结构、CTA、模板 | 把优秀视频拆成可复用方法论 |
| Editing Agent   | 商品、脚本、RAG 候选素材 | EditingPlan 智能分镜方案 | 把脚本转成可执行生成方案 |
| Retry Agent     | 错误、分镜、重试次数 | 是否重试、如何改参数     | 提高生成稳定性       |
| Analytics Agent | mock 指标            | 中文优化建议             | 展示反馈优化能力     |

### 11.2 LangGraph 的作用

LangGraph 用在两个核心文件：

- `editing_graph.py`
- `pipeline_graph.py`

它的作用是把多个步骤组织成工作流，而不是散落在一个大函数里。

```mermaid
flowchart TD
  A[输入上下文] --> B[准备商品/脚本/素材]
  B --> C[构造全局查询 embedding]
  C --> D[RAG TopK 检索候选素材]
  D --> E[构造 LLM payload]
  E --> F[LLM 生成智能分镜方案]
  F --> G[校验字段/时长/素材 ID]
  G --> H[修复重复素材或置空]
  H --> I[输出 EditingPlan]
```

这个图可以用来回答“这和封装函数有什么区别”：如果只是函数封装，通常是输入脚本、拼字符串、返回结果；现在的 Editing Graph 有明确的状态流转、RAG 检索节点、LLM planning 节点、校验修复节点和 fallback 节点。它不是让 LLM 直接剪视频，而是让 LLM 在 RAG 候选素材和生成约束内做分镜生成计划。

视频 Pipeline 的 LangGraph 更复杂：

```mermaid
flowchart TD
  A[load_task] --> B[prepare_shots]
  B --> C[generate_shots]
  C --> D{has_failed_shot}
  D -->|yes| E[retry_decision]
  E --> F{can_retry}
  F -->|yes| C
  F -->|no| G[mark_failed]
  D -->|no| H[stitch_video]
  H --> I[postprocess]
  I --> J[callback_succeeded]
```

### 11.3 Retry Agent 具体效果

以 Seedance duration 错误为例：

```text
第一次请求：
duration 参数被模型接口拒绝 -> 400 InvalidParameter

Retry Agent：
识别错误中包含 duration -> 把 duration_sec 修正为更稳定的值 -> 允许重试

第二次请求：
使用修正后的参数生成 -> 成功概率提高
```

它的意义是：

- 避免一次参数错误就导致整条视频失败。
- 把失败处理逻辑集中在 Agent 中，方便后续扩展。
- trace 中可以记录为什么重试、重试改了什么。

### 12.4 答辩时可以强调的点

- 系统是端到端的，不只是 prompt demo。
- Node 和 Python 职责清晰，前端只调用 Node。
- Python 体现了 Agent 开发和 LangGraph 编排。
- 参考视频拆解对应比赛要求中的“找参考 -> 提炼方法论 -> 生产剧本”。
- 素材分析结果参与剪辑计划。

- Retry Agent 解决真实模型调用的不稳定问题。
- trace 让生成过程可解释、可排查。
- 单分镜重生成让系统更接近真实剪辑工具。

## 十三、已知问题与后续扩展

### 13.1 已知问题

- Seedance 1.5 Pro 图生视频有时会对 `duration` 参数返回 400。当前 Retry Agent 会在重试时修正时长，记录见 `docs/known-issues.md`。
- 数据看板当前使用 mock analytics，用于展示效果分析闭环，不代表真实投放数据。
- TTS/BGM 当前是 provider-ready 扩展点，P1 demo 重点是字幕渲染、音频保留和后处理链路。

### 13.2 后续扩展方向

- 接入真实投放数据，替换 mock analytics。
- 增加 A/B 测试任务和多版本视频对比。
- 增加合规审核 Agent，例如敏感词、夸大宣传、平台规则检查。
- 将 SQLite 升级为 PostgreSQL，并引入 pgvector 存储 embedding。
- 增加任务队列和后台 worker，提高长任务稳定性。
- 增加对象存储，将 `storage/` 替换为 OSS/S3。
- 将 TTS/BGM provider 真正接入生产模型。
